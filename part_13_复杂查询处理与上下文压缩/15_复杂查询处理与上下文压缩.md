## 学习目标

1. 理解多跳查询和复杂查询的处理方法
2. 掌握上下文压缩（Context Compression）技术
3. 能够处理长文本和跨文档的复杂查询场景

## 关联知识框架知识点

- **kp_024**: Query Decomposition查询分解 - 对于复杂问题，将其拆解为多个简单子问题，分别检索后再综合回答。
- **kp_025**: CRAG可纠正检索增强生成 - 通过评估检索结果的相关性，对低质量检索进行主动降级。
- **kp_029**: Context Compression上下文压缩 - 检索结果常含冗余信息，需要压缩。

## 一、背景与问题引入

### 1.1 复杂查询的挑战

在实际应用中，用户的问题往往比简单的"查找定义"复杂得多：

| 查询类型 | 示例 | 挑战 |
|----------|------|------|
| **多跳查询** | "《时间简史》的作者还写过什么书？" | 需要先找到作者，再查其他作品 |
| **比较查询** | "Python和Java在Web开发上各有什么优缺点？" | 需要从多个文档中提取对比信息 |
| **关系推理** | "哪些公司采用了RAG技术开发了智能问答系统？" | 需要理解实体间的关系 |
| **数值查询** | "2024年营收增长超过50%的公司有哪些？" | 需要数值比较和筛选 |

### 1.2 上下文膨胀问题

RAG系统检索返回的文档常包含大量冗余信息：

- 文档块可能包含与查询无关的背景描述
- 上下文窗口宝贵，无关内容挤占关键信息
- 长上下文增加LLM的计算成本和推理时间

## 二、Query Decomposition 查询分解

### 2.1 核心思想

Query Decomposition（查询分解）的核心理念是"化繁为简"：

```
复杂问题 → 拆解为多个简单子问题 → 分别检索 → 综合回答
```

### 2.2 分解策略

| 策略 | 适用场景 | 示例 |
|------|----------|------|
| **顺序分解** | 后续问题依赖前一步答案 | "谁写的《战争与和平》？它出版于哪年？" |
| **并行分解** | 各子问题独立可并行检索 | "Python、Java、Go各自的优缺点是什么？" |
| **层次分解** | 主问题包含多个子主题 | "介绍人工智能，包括定义、发展历史、应用领域" |

### 2.3 工作流程

```
用户问题："《星际穿越》导演的其他科幻电影有哪些？"

步骤1：分解
├── 子问题A：谁是《星际穿越》的导演？
└── 子问题B：该导演还拍过哪些科幻电影？

步骤2：分别检索
├── 检索A答案：克里斯托弗·诺兰
└── 检索B答案：《盗梦空间》、《蝙蝠侠：黑暗骑士》等

步骤3：综合回答
综合子问题答案，形成完整回应
```

## 三、多跳查询处理

### 3.1 什么是多跳查询？

多跳查询（Multi-hop Query）需要跨越多个步骤推理才能得到答案：

- 第一跳：定位相关实体或信息
- 后续跳：基于前一步结果继续查询
- 最终：综合多跳结果形成答案

### 3.2 多跳推理的难点

1. **实体链接**：如何正确关联跨文档的同一实体
2. **路径追踪**：如何记录推理路径保证可解释性
3. **误差累积**：每一步的误差可能逐级放大

### 3.3 解决思路

| 方法 | 说明 |
|------|------|
| **迭代检索** | 每跳检索后重新评估，决定是否继续 |
| **子问题队列** | 将子问题加入队列，依次处理 |
| **图结构推理** | 构建实体关系图，支持路径推理 |

## 四、CRAG 可纠正检索增强

### 4.1 核心思想

CRAG（Corrective Retrieval Augmented Generation）通过评估检索结果质量，主动采取不同策略：

```
检索结果 → 质量评估
    ↓
质量高 → 直接用于生成
质量中 → 知识去污（Knowledge Refinement）
质量低 → 网络搜索替代 / 依赖自身知识
```

### 4.2 质量评估维度

| 维度 | 评估内容 |
|------|----------|
| **相关性** | 文档与查询的话题相关程度 |
| **置信度** | 答案在文档中的明确程度 |
| **覆盖度** | 文档覆盖查询内容的完整性 |

### 4.3 知识去污（Knowledge Refinement）

当检索结果质量中等时，对结果进行提纯：

- 过滤掉不相关的片段
- 保留核心相关内容
- 重新组织后用于生成

## 五、Context Compression 上下文压缩

### 5.1 为什么需要压缩？

检索返回的文档常包含大量冗余信息：

- **Token浪费**：无关内容消耗宝贵的上下文额度
- **噪音干扰**：关键信息被稀释
- **成本增加**：长上下文带来更高的LLM调用成本

### 5.2 压缩策略类型

| 策略 | 原理 | 适用场景 |
|------|------|----------|
| **LLMCompactor** | 使用LLM判断并提取关键句 | 需要高精度压缩 |
| **RecursiveCompression** | 递归分割并选择最相关部分 | 长文档处理 |
| **ContextualCompression** | 保留上下文信息的压缩 | 维持语义完整 |
| **RECOMP** | 添加摘要增强的压缩 | 文档级别压缩 |

### 5.3 压缩流程

```
原始检索结果（可能1000字）
    ↓
相关性评估 + 关键信息提取
    ↓
压缩内容（可能200字）
    ↓
用于答案生成
```

## 六、实际应用架构

### 6.1 复杂查询处理完整流程

```
用户复杂查询
    ↓
Query Decomposition（分解）
    ↓
并行/串行检索子问题
    ↓
结果质量评估（CRAG）
    ↓
Context Compression（压缩）
    ↓
综合答案生成
```

### 6.2 策略选择指南

| 场景 | 推荐策略 |
|------|----------|
| 多跳推理问题 | Query Decomposition + 迭代检索 |
| 检索结果质量不稳定 | CRAG + 质量评估 |
| 长文档检索 | Context Compression |
| 比较类问题 | 并行分解 + 结果对比 |

## 八、总结

| 技术 | 核心思想 | 解决的问题 |
|------|----------|------------|
| **Query Decomposition** | 复杂问题拆解为简单子问题 | 多跳推理困难 |
| **多跳查询处理** | 迭代检索和逐步推理 | 跨文档关联 |
| **CRAG** | 评估检索质量，动态调整策略 | 检索结果不可靠 |
| **Context Compression** | 去除冗余，提取关键信息 | 上下文膨胀 |

复杂查询处理和上下文压缩是企业级RAG系统的必备能力，它们共同解决了"查准"和"查全"的问题，让RAG系统能够应对真实世界的复杂问答场景。
