## 2.1 RAG 三步走详解

RAG 的名称来自三个核心步骤：**R**etrieve、**A**ugment、**G**enerate。这三步看似简单，但每一步都有很多技术细节值得深入理解。

### 2.1.1 第一步：检索（Retrieve）

**目标**：根据用户问题，从知识库中找到最相关的文档片段。

**工作流程**：

```python
# 检索流程示意
user_query = "RAG的Embedding是什么？"

# Step 1: 将用户问题转换为向量
query_vector = embedding_model.encode(user_query)
# 结果示例: [0.123, -0.456, 0.789, ...]  # 1536维向量

# Step 2: 在向量数据库中进行相似度搜索
# 找出与问题向量最"接近"的文档向量
results = vector_db.search(
    query_vector,
    top_k=5,  # 返回最相关的5个文档
    similarity_threshold=0.7  # 相似度阈值
)

# Step 3: 返回相关文档及其相似度分数
# [
#   {"content": "Embedding是将文本转换为向量的技术...", "score": 0.92},
#   {"content": "向量数据库存储文本的向量表示...", "score": 0.85},
#   ...
# ]
```

**为什么需要检索，而不是直接用整个知识库？**

```
场景：企业知识库有 10000 页文档

直接塞给模型：
- GPT-4o 上下文窗口：128K tokens ≈ 6-7万字 ≈ 约 70 页
- 10000 页 >> 70 页
- 根本塞不进去！

检索方案：
- 只取出与问题最相关的几页（如 5 页 ≈ 1 万字）
- 塞入模型，完美适配上下文窗口
```

### 2.1.2 第二步：增强（Augment）

**目标**：将检索到的文档与用户问题组合，构建一个"有上下文"的提示词。

**增强策略**：

```python
# 策略一：简单拼接（最常用）
prompt = f"""
用户问题：{user_query}

参考文档：
{retrieved_doc_1}
{retrieved_doc_2}
{retrieved_doc_3}

请根据参考文档回答用户问题。
"""

# 策略二：对话格式
prompt = f"""
你是一个专业的技术文档助手。

以下是一些参考文档：
{retrieved_docs}

现在请回答这个问题：{user_query}

要求：
1. 仅基于提供的文档回答
2. 如果文档中没有相关信息，请说明
3. 引用文档中的具体内容
"""

# 策略三：带思考指引
prompt = f"""
用户问题：{user_query}

我找到了以下相关文档：
{format_docs(retrieved_docs)}

请按以下步骤回答：
1. 先理解用户问题的核心意图
2. 从文档中找出相关信息
3. 综合给出准确回答
4. 注明参考来源
"""
```

**增强的关键点**：

| 要素 | 说明 |
|------|------|
| 上下文长度 | 不能超过模型的上下文窗口 |
| 文档排序 | 最相关的文档放在最前面（注意力权重） |
| 噪声过滤 | 移除无关或低质量的检索结果 |
| 来源标注 | 让模型知道答案来自哪里 |

### 2.1.3 第三步：生成（Generate）

**目标**：让大模型基于增强后的 Prompt 生成回答。

```python
# 生成流程
response = llm.chat(
    messages=[
        {"role": "system", "content": "你是一个专业的技术助手，基于提供的文档回答问题。"},
        {"role": "user", "content": augmented_prompt}
    ],
    temperature=0.7,  # 控制创造性，RAG 场景通常偏低
    max_tokens=1000   # 限制回答长度
)

# 生成的回答示例：
# "根据文档，Embedding 是将文本转换为向量表示的技术...
#  它能够捕捉文本的语义信息，使得语义相似的文本在向量空间中相近..."
```

**生成阶段的注意事项**：

```
好的生成：
✓ 只使用检索到的信息回答
✓ 引用具体文档内容
✓ 承认知识的局限性

不好的生成：
✗ 完全忽略检索内容，自由发挥
✗ 混合"记忆"和检索内容，无法区分来源
✗ 过度发挥，添加文档中没有的细节
```

## 2.2 广义 RAG vs 狭义 RAG

### 2.2.1 广义 RAG

广义 RAG 泛指所有"先检索外部知识，再增强生成"的架构模式。

**典型案例**：

1. **联网搜索 + LLM**
   - 用户问："今天北京天气怎么样？"
   - 系统先搜索互联网获取天气数据
   - LLM 基于搜索结果生成回答

2. **Perplexity AI**
   - 实时联网搜索
   - 自动整理搜索结果
   - 生成带引用的回答

3. **Google AI Overview**
   - 搜索 + LLM 总结
   - 顶部直接显示答案

**架构模式**：

```
用户问题 → 检索（公开互联网）→ 增强 → 生成 → 回答
```

### 2.2.2 狭义 RAG

狭义 RAG 特指基于**私有知识库 + 向量检索**的增强生成系统。

**核心差异**：

| 维度 | 广义 RAG | 狭义 RAG |
|------|----------|----------|
| **检索源** | 公开互联网 | 私有知识库 |
| **数据可控性** | 低（依赖搜索引擎） | 高（完全自主） |
| **更新频率** | 实时 | 可自定义 |
| **权限控制** | 困难 | 容易实现 |
| **典型场景** | 通用问答、新闻 | 企业知识库、客服 |

**架构模式**：

```
用户问题 → 检索（私有知识库）→ 增强 → 生成 → 回答
```

### 2.2.3 本课程的重点

**后续所有内容都聚焦在狭义 RAG**：

```
┌─────────────────────────────────────────┐
│           狭义 RAG 系统                 │
├─────────────────────────────────────────┤
│                                         │
│  用户问题 ──→ 检索 ──→ 增强 ──→ 生成    │
│     ↑                        ↓          │
│     └─────── 私有知识库 ←────┘          │
│                                         │
└─────────────────────────────────────────┘
```

## 2.3 RAG 在 LLM 应用生态中的定位

### 2.3.1 LLM 应用技术栈

RAG 位于 LLM 应用技术栈的**应用架构层**。

```
┌─────────────────────────────────────────────────────────┐
│                    应用层                               │
│         智能客服 / 文档问答 / 知识管理                    │
├─────────────────────────────────────────────────────────┤
│                 应用架构层                               │
│      RAG（知识增强）│ Agent（任务规划）│ Fine-tuning     │
├─────────────────────────────────────────────────────────┤
│                   数据层                                 │
│           企业文档 / 知识库 / 数据库                       │
├─────────────────────────────────────────────────────────┤
│                  模型层                                   │
│        OpenAI / Qwen / Llama / Claude                  │
└─────────────────────────────────────────────────────────┘
```

### 2.3.2 RAG 与其他方案的互补关系

**RAG + Agent（智能体）**：

```python
# Agent 负责规划任务
# RAG 负责提供知识

agent_plan = """
1. 判断用户意图（查询订单 / 退换货 / 技术咨询）
2. 如果是技术咨询 → 调用 RAG 检索产品文档
3. 如果是订单查询 → 调用订单系统 API
4. 综合所有信息生成最终回答
"""
```

**RAG + Fine-tuning**：

```python
# RAG 负责提供知识（实时、可更新）
# Fine-tuning 负责定制回答风格

system_prompt = """
你是一个{公司名}的客服助手。
- 语气要亲切、专业
- 使用"请问有什么可以帮您"等标准开场白
- RAG 提供产品知识，你负责组织回答
"""
```

## 2.4 实战：一个简单的 RAG 流程

### 2.4.1 完整代码示例

```python
"""
一个最简单的 RAG 问答系统演示
"""

# 1. 准备知识库（通常是 PDF/Word 文档，这里用简化的文本）
documents = [
    "RAG 是检索增强生成（Retrieval-Augmented Generation）的缩写。",
    "RAG 由三个步骤组成：检索（Retrieve）、增强（Augment）、生成（Generate）。",
    "Embedding 是将文本转换为向量表示的技术。",
    "向量数据库用于存储和检索文本向量。",
    "Chroma 是一个轻量级的向量数据库。"
]

# 2. 初始化组件
from embedding import EmbeddingModel
from vector_db import VectorDB
from llm import LLM

embedding_model = EmbeddingModel("text-embedding-3-small")
vector_db = VectorDB("chroma")
llm = LLM("gpt-4o")

# 3. 将文档存入向量数据库
for i, doc in enumerate(documents):
    vector = embedding_model.encode(doc)
    vector_db.add(f"doc_{i}", vector, {"text": doc})

# 4. RAG 问答流程
def rag_query(question: str) -> str:
    # Step 1: 检索
    question_vector = embedding_model.encode(question)
    results = vector_db.search(question_vector, top_k=2)
    
    # Step 2: 增强
    context = "\n".join([r["text"] for r in results])
    prompt = f"""基于以下参考文档回答问题。
    
参考文档：
{context}

问题：{question}

回答（引用参考文档）：
"""
    
    # Step 3: 生成
    response = llm.chat(prompt)
    return response

# 5. 测试
answer = rag_query("RAG 是由哪三个步骤组成的？")
print(answer)
# 输出：RAG 由检索（Retrieve）、增强（Augment）、生成（Generate）三个步骤组成。
```

### 2.4.2 关键代码解释

| 代码段 | 作用 |
|--------|------|
| `EmbeddingModel` | 将文本转换为向量 |
| `VectorDB` | 存储和检索向量 |
| `LLM` | 生成自然语言回答 |
| `vector_db.add()` | 将文档存入知识库 |
| `vector_db.search()` | 根据问题检索相关文档 |
| `llm.chat()` | 生成最终回答 |

## 本节总结

### 核心要点

1. **RAG 三步走**：检索（找资料）→ 增强（组装 Prompt）→ 生成（模型回答）
2. **广义 vs 狭义 RAG**：广义的检索源是互联网，狭义的检索源是私有知识库
3. **RAG 生态定位**：处于应用架构层，与 Agent、Fine-tuning 各司其职
