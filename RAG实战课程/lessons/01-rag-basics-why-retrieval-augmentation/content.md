# 第一课：RAG基础 - 为什么需要检索增强

## 本节概述

本节课将带你理解大模型为什么会"一本正经地胡说八道"，以及 RAG（检索增强生成）如何解决这个问题。你将掌握：

- 大模型的四大知识局限
- 三种知识注入方案的对比
- 为什么 RAG 是当前最务实的知识增强路径

**学习时长**：约 2-3 小时

---

## 1.1 大模型的"知识困境"

想象这样一个场景：你是一家金融公司的分析师，需要回答客户关于公司年报的问题。你问大模型：

> "我们公司2024年第四季度的净利润是多少？"

大模型胸有成竹地回答：

> "根据公开数据，贵公司2024年第四季度净利润为 3.2 亿元，同比增长 15%。"

听起来很专业，对吧？但问题是——**这个数字是大模型自己编造的**。真实的财报可能显示是 2.8 亿元，或者这个产品线根本不盈利。

这就是大模型的"知识困境"。让我们深入分析大模型面临的四堵知识围墙。

### 1.1.1 幻觉问题（Hallucination）

**什么是幻觉？**

幻觉是指大模型在生成文本时，产出看似流畅合理、但与事实不符或完全虚构的内容。这是最让开发者头疼的问题。

**生活中的类比**：

就像一个特别会讲故事的朋友，他说话头头是道、逻辑清晰，但你仔细一查，发现他说的很多事情都是"艺术加工"过的。他不是故意骗你，而是真的把自己想象的内容当成了事实。

**技术解释**：

大模型的本质是一个"概率预测机器"。它根据训练数据中的模式，预测下一个最可能的词（Token）。当它遇到不确定的问题时，它不会说"我不知道"，而是会**自信地编造一个看起来合理但完全错误的答案**。

```
问题：我公司年假制度是什么？
理想回答：抱歉，我不知道您公司的具体制度，请咨询HR。
实际回答：根据劳动法规定，员工享有带薪年假...
         （大模型开始'创作'一份根本不存在的制度）
```

**在企业场景中的风险**：

| 领域 | 幻觉风险 | 后果 |
|------|---------|------|
| 医疗 | 给出错误的用药剂量 | 危及患者生命 |
| 法律 | 引用不存在的法规 | 导致错误法律建议 |
| 金融 | 虚构财务数据 | 投资决策失误 |
| 客服 | 产品参数错误 | 客户投诉、流失 |

### 1.1.2 知识截止（Knowledge Cutoff）

**什么是知识截止？**

每个大模型都有一个训练数据的截止日期。在这个日期之后发生的事件、发布的框架、更新的事实，模型完全不知道。

**生活中的类比**：

就像一个学生参加一场"闭卷考试"。考试范围是截至去年底的知识点。即使今年发生了天大的事（比如新冠疫情、新的诺贝尔奖），他也无法回答相关内容。

**主流模型的知识截止日期**（截至2026年）：

| 模型 | 知识截止日期 |
|------|------------|
| GPT-5 | 2024年10月 |
| Claude 4.6 | 2026年1月 |
| Qwen3.5 | 2025年底 |
| DeepSeek | 2025年6月 |

**实际影响**：

```
问题1："上周发布的LangChain新版本有什么特性？"
回答：抱歉，我不知道，因为我的知识截止到2024年10月。

问题2："iPhone 17 什么时候发布？"
回答：我无法回答这个问题，因为它是未来的事件。
```

### 1.1.3 领域盲区（Domain Blindness）

**什么是领域盲区？**

大模型的训练数据来自公开互联网，它对你公司的内部文档、私有数据库、行业专有知识几乎一无所知。

**生活中的类比**：

就像一个全科医生，他懂感冒发烧、高血压糖尿病，但对你公司特有的"弹性福利计划"、"项目奖金计算规则"一无所知。他甚至不知道你公司的产品叫什么名字。

**企业场景中的具体表现**：

```
通用问题：大模型能回答
- "如何报销差旅费？"（通用财务知识）
- "Python怎么连接数据库？"（编程知识）

私有问题：大模型无法回答
- "我们公司的年假怎么计算？"（内部政策）
- "产品X的最大并发数是多少？"（产品规格）
- "和客户A的合同什么时候到期？"（商业数据）
```

### 1.1.4 上下文窗口限制（Context Window Limit）

**什么是上下文窗口限制？**

即使你想通过 Prompt 把所有知识"塞给"模型，也会撞上另一堵墙——上下文窗口的长度限制。

**生活中的类比**：

就像你参加开卷考试，但只允许带一张 A4 纸的参考资料。如果你的知识库有 1000 页书，你只能选择性地抄写最重要的内容到那张纸上。

**主流模型的上下文限制**：

| 模型 | 上下文长度 | 约等于中文 |
|------|-----------|-----------|
| GPT-4o | 128K tokens | 约6-7万字 |
| Claude 3.5 | 200K tokens | 约10万字 |
| Gemini 1.5 | 1M tokens | 约50万字 |

**为什么这是个问题**：

```
场景：你的企业知识库有 5000 页文档

计算：
- 5000页 ≈ 250万字
- 按中文 ≈ 125万 token
- GPT-4o 的 128K 只能容纳约 5%

结论：不可能把所有知识一次性塞给模型
```

**这直接催生了 RAG 的核心设计思路**：

> **不把所有知识塞给模型，而是每次只检索最相关的片段**

## 1.2 三种知识注入方案对比

面对大模型的知识局限，业界发展出了三种主流的解决方案。理解它们的差异，是选择正确技术路线的前提。

### 方案对比总览

| 维度 | Prompt Engineering | Fine-tuning | RAG |
|------|-------------------|-------------|-----|
| **核心思路** | 在提示词中塞入上下文 | 用领域数据重新训练模型 | 先检索再生成 |
| **知识更新速度** | 即时（改 Prompt 即可） | 慢（需重新训练） | 快（更新知识库即可） |
| **成本** | 低 | 高（GPU + 数据标注） | 中（向量数据库 + API） |
| **知识容量** | 受限于上下文窗口 | 受限于训练数据量 | 理论上无限 |
| **幻觉控制** | 一般 | 较好（领域内） | 好（有据可查） |
| **适用场景** | 简单任务、少量上下文 | 风格/格式定制、专业术语 | 知识密集型问答 |

### 1.2.1 Prompt Engineering（提示词工程）

**原理**：通过精心设计的提示词（Prompt），引导模型在回答时"考虑"特定的上下文信息。

**优点**：
- 实现简单，不需要编程基础
- 零成本，不需要额外的模型训练
- 实时生效，修改 Prompt 立即可见

**缺点**：
- 受限于上下文窗口，无法处理大量知识
- 效果不稳定，同样的 Prompt 可能产生不同结果
- 难以精确控制模型的回答范围

**适用场景**：

```python
# 适用：简单、简短的上下文
prompt = """
你是一个客服助手。请用友好的语气回答客户问题。

已知信息：
- 我们的客服工作时间是 9:00-18:00
- 退货政策是 7 天无理由退货
- 我们的电话是 400-123-4567

客户问题：你们的退货政策是什么？
"""

# 不适用：大量知识（如 100 页产品手册）
```

### 1.2.2 Fine-tuning（微调）

**原理**：使用特定领域的数据对预训练模型进行额外训练，让模型"学会"这个领域的知识。

**优点**：
- 模型能够"内化"领域知识
- 回答风格可定制
- 推理速度快（不需要检索步骤）

**缺点**：
- 训练成本高：需要 GPU、数据标注人员
- 更新周期长：每次更新需要重新训练
- 难以调试：知识融入参数，出错难定位

**成本对比（以 7B 参数模型为例）**：

| 项目 | 成本 |
|------|------|
| GPU 使用（A100 单卡 4 小时） | ¥200-400 |
| 数据标注（1000 条） | ¥500-2000 |
| 一次迭代总成本 | ¥700-2400 |
| 每月更新 2 次 | ¥1400-4800/月 |

### 1.2.3 RAG（检索增强生成）

**原理**：在生成回答之前，先从外部知识库检索相关文档，然后将检索结果拼入 Prompt，让模型"参考"这些文档来回答。

**优点**：
- 知识与推理解耦：更新知识库不需要重新训练
- 回答可溯源：每条回答都能追溯到具体文档
- 成本可控：主要是向量数据库 + API 调用费用
- 易于调试：问题可定位到具体文档

**缺点**：
- 需要维护知识库和检索系统
- 检索质量直接影响回答质量
- 增加了系统复杂度

**核心公式**：

```
RAG 回答 = LLM(用户问题 + 检索到的相关文档)
```

### 1.2.4 选择指南

```
问题分析 → 选择策略

│
├─ 知识量少（< 几千字）？
│   └─ → Prompt Engineering
│
├─ 知识频繁变化？
│   └─ → RAG（首选）
│
├─ 需要定制回答风格/格式？
│   └─ → Fine-tuning（可选 RAG 补充）
│
├─ 知识密集型问答 + 需要可溯源？
│   └─ → RAG（强烈推荐）
│
└─ 知识非常专业/垂直？
    └─ → RAG + Fine-tuning 结合
```

## 1.3 RAG 的核心思想：让模型"开卷考试"

### 1.3.1 从"闭卷"到"开卷"

**传统的大模型推理 = 闭卷考试**

模型只能依赖训练时"记住"的知识来回答问题。遇到不知道的内容，只能凭"猜测"。

```
用户问题
    ↓
┌─────────────────┐
│   大模型        │  ← 只能靠"记忆"回答
│  （闭卷考试）   │
└─────────────────┘
    ↓
模型回答（可能幻觉）
```

**RAG = 开卷考试**

在回答之前，先让模型翻阅相关的参考资料，然后基于这些资料来组织答案。

```
用户问题
    ↓
┌─────────────────┐
│   检索系统      │  ← 先查资料
│  （翻书环节）   │
└─────────────────┘
    ↓ 相关文档
┌─────────────────┐
│   大模型        │  ← 参考资料回答
│  （开卷考试）   │
└─────────────────┘
    ↓
有据可查的回答
```

### 1.3.2 RAG 三步走

RAG 的名称来自三个核心步骤的首字母：**R**etrieve-**A**ugment-**G**enerate

#### 第一步：检索（Retrieve）

根据用户的问题，从外部知识库中找到最相关的文档片段。

```python
# 示意代码
user_question = "我们公司年假制度是什么？"

# 1. 将问题向量化（转换为数学向量）
question_vector = embedding_model.encode(user_question)

# 2. 在向量数据库中搜索最相似的文档
relevant_docs = vector_db.search(question_vector, top_k=3)

# 检索结果示例
# [
#   "第一章 第三条：员工入职满一年后享受带薪年假...",
#   "年假制度：工作1-3年5天，3-5年10天，5年以上15天...",
#   "请假流程：需提前在OA系统提交申请..."
# ]
```

#### 第二步：增强（Augment）

将检索到的文档片段与用户问题拼接在一起，构成增强后的 Prompt。

```python
# 构造增强 Prompt
augmented_prompt = f"""
你是一个企业HR助手。请根据以下资料回答用户问题。
如果资料中没有相关信息，请如实告知。

【用户问题】
{user_question}

【参考资料】
{'-' * 50}
{relevant_docs[0]}
{'-' * 50}
{relevant_docs[1]}
{'-' * 50}
{relevant_docs[2]}
{'-' * 50}

请回答：
"""
```

#### 第三步：生成（Generate）

将增强后的 Prompt 送入大模型，生成最终回答。

```python
# 调用大模型生成回答
response = llm.chat(messages=[
    {"role": "system", "content": "你是一个专业的HR助手。"},
    {"role": "user", "content": augmented_prompt}
])

# 生成的回答示例：
# "根据公司制度，员工年假安排如下：
#  - 工作满1年：5天年假
#  - 工作满3年：10天年假
#  - 工作满5年：15天年假
# 请假需提前在OA系统提交申请..."
```

┌─────────────────────────────────────────────────────────────────┐

## 1.4 常见误区与避坑指南

### 误区一：模型越大，幻觉越少

**错误认知**：幻觉问题与模型规模简单线性相关。

**事实**：
- 即使是最先进的模型，在面对训练数据中未覆盖的领域知识时，仍然会产生幻觉
- RAG 降低幻觉的前提是：知识库质量高 + 检索准确

### 误区二：用了 RAG 就能 100% 消除幻觉

**错误认知**：RAG = 完美答案生成器。

**事实**：
- 如果检索到的文档本身有错误 → 模型仍会幻觉
- 如果检索结果与问题不相关 → 模型仍会出错
- **RAG 降低幻觉，但前提是知识库和检索都高质量**

### 误区三：遇到问题就上 Fine-tuning

**错误认知**：Fine-tuning 是万能解。

**事实**：
- 不少团队花大量时间标注数据、训练模型
- 最后发现效果还不如一个设计良好的 RAG 系统
- **经验法则：先用 RAG 验证可行性，只有 RAG 无法满足要求时，再考虑 Fine-tuning**
